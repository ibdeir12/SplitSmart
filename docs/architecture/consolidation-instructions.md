   | Topic | Proposed clarification text |
   |---|---|
   | Payment availability and confirmation, A-D1 / D-3 | In the MVP, the signed-in recorder is the paying member; recording on behalf of another payer is not supported. A new payment may use only the current amount the payer owes the receiver in that group, less amounts already Awaiting Confirmation in the same direction. Reservations do not change balances. Confirmation must recheck the current debt; if the payment now exceeds it, confirmation is refused, the payment remains Awaiting Confirmation, and the receiver may decline it. Never settle a payment using a debt from another group. |
   | Meaning of settled membership, A-D2 | For removal or leaving, a member is settled only when every pairwise balance with that member in that group is 0.00. A scalar overall position of 0.00 can conceal debts to different people and is insufficient. This is an explicit proposed clarification of FR-011 and US2-AS3/US2-AS6, not an unrecorded extra service guard.    | Pending work on departure, A-D2 | In the same operation as a permitted departure, cancel each Pending expense for which the departing member is creator, payer, participant, or required approver; cancel each Awaiting Confirmation payment they send or receive; release the associated reservations. Keep all source records and genuine decisions. Record cancellation separately with its initiating actor, reason, and time. Cancellation changes no balance and does not impersonate an Approver or payment receiver. |
   | Creator succession, A-D2 | The current Group Creator role transfers on that member's permitted departure to the remaining active member with the earliest current membership join time, breaking ties by ascending user UUID. The successor has all creator management rights. Preserve the original creator attribution. If no active member remains, archive the group with its history; expose no further member operations. No general group-deletion or ownership-transfer feature is introduced. |
   | Expense discovery, A-D3 | Every current group member can list and reopen its saved expenses, including Pending, Approved, Rejected, and lifecycle-Cancelled records, after restart. The list includes stable expense IDs. An empty group has an empty expense list. A former member cannot access the group through an old ID or notification. |
   | All-groups balances, A-D4 | Show a separate net amount for every counterparty across the signed-in member's current groups, with the contributing per-group amounts, plus an overall net position equal to the sum of those counterparty amounts. Do not simplify debts between different counterparties. Cross-group totals are informational; payments remain group-specific. |
   | Receipts | One optional receipt is accepted only if its actual content decodes as JPEG or PNG and its size is at most **5,000,000 bytes (5 MB)**. The boundary is inclusive. A filename extension alone is insufficient. Invalid attachment input is refused while other form entries are retained; choosing no attachment remains valid. An unavailable stored image produces a receipt-unavailable message without hiding the expense or changing balances. This resolves R-06's ambiguous size unit as an MVP planning limit. |
   | Operational failures | A storage/startup failure must show a safe actionable message. A failed mutation must say whether it was saved, not saved, or its outcome is unknown. Retain input; check operation status before retrying an unknown outcome. Never silently reset the data store, report false success, or repeat a mutation without resolving its prior result. Slow work shows a loading state and prevents duplicate submission. The local MVP needs no network connection; network failure belongs to deferred clients. |

   | Decision | Required architecture change |
   |---|---|
   | D-1: ports | Put repository interfaces, `ReceiptStore`, `PasswordHasher`, and `TransactionRunner`/`UnitOfWork` in `com.splitsmart.service.port`. Inject `java.time.Clock`. Put JDBC implementations and database startup/migration code in `persistence`, receipt filesystem implementation in `storage`, and PBKDF2 implementation in `security`. `app.AppContext` wires concrete adapters.    | D-2: transaction ownership | The top-level use case owns one unit of work.
