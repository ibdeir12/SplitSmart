## Conventions

| Topic | Rule |
|-------|------|
| Identifiers | `UUID`, generated by the service layer. A user's UUID never changes, including when the user leaves and later rejoins a group. |
| Timestamps | `Instant` (UTC), always taken from the injected `java.time.Clock`. One unit of work uses one `now` value for every row it writes. Stored as `TIMESTAMP WITH TIME ZONE`. |
| Business dates | `LocalDate` (expense date, payment date, report range). Stored as `DATE`. |
| Money | `Money`: a `BigDecimal` of scale 2, parsed from text with `new BigDecimal(String)` (D-4). Never `float` or `double`, including in fixtures and intermediate values. Compared with `compareTo`, never `equals`. |
| Text boundaries | Amounts and percentages enter as decimal strings and leave formatted with exactly two decimal places. |
| Nullability | Column "Null" = **no** means required. `[0..1]` in a type means optional. |
| Sign convention | In every viewer-relative balance type, a **positive** amount means the viewing member owes the counterparty, a **negative** amount means the counterparty owes the viewing member, and 0.00 means settled. |
| Monetary sources | Only Approved expense shares and Confirmed payments are monetary source records for balances. Pending reservations limit new payment recording and never change a displayed balance. A `LifecycleEvent` is an audit record, not a monetary posting. Balances are always derived; no balance or posting table exists. |
| Deletion | No cascading deletes. Users, groups, memberships, expenses, shares, genuine decisions, payments, lifecycle events, and referenced receipts are retained. The only permitted source-record deletion is a creator deleting their own Pending expense (FR-047), which the service performs explicitly within one unit of work. |

## Value types

### Money (FR-014 – FR-016, FR-031 – FR-037, NFR-001)

| Aspect | Rule |
|--------|------|
| Representation | `BigDecimal`, scale 2, unbounded precision in memory. |
| Parsing (`Money.parse(String)`) | Trim; refuse empty, exponent notation, and non-numeric text; construct with `new BigDecimal(String)`; refuse scale greater than 2; then `setScale(2, RoundingMode.UNNECESSARY)`. |
| Input range | Expense and payment amounts: 0.01 to 100,000.00 inclusive (FR-016, FR-037), checked by `AmountRules`. |
| Computed values | A share may be 0.00 (for example 0.01 split among three). Balances, counterparty totals, overall positions, and report totals are signed and may exceed 100,000.00; the input range does not apply to them. |
| Storage | Source amounts: `DECIMAL(12,2)`, read and written only with `ResultSet.getBigDecimal` and `PreparedStatement.setBigDecimal`. Derived values are never stored. |

### Percentage (FR-015)

| Aspect | Rule |
|--------|------|
| Representation | `BigDecimal`, scale 2, parsed from text like `Money`. |
| Per participant | Greater than 0.00 and at most 100.00, at most two decimal places. |
| Total | Exactly 100.00 by `compareTo`; otherwise refused with the current total shown. |
| Storage | `DECIMAL(5,2)`. |

### Split calculation (SplitCalculator; FR-014, FR-015, FR-020, NFR-001)

All rounding is in `SplitCalculator`, with explicit scale and `RoundingMode`:

- **Equal**: `base = amount.divide(BigDecimal.valueOf(n), 2, RoundingMode.DOWN)`;
  `leftoverCents = amount.subtract(base.multiply(BigDecimal.valueOf(n))).movePointRight(2).intValueExact()`;
  the first `leftoverCents` participants in listed order receive `base + 0.01`, the rest `base`.
- **Percentage**: `raw_i = amount.multiply(p_i).movePointLeft(2)` (exact, scale 6);
  `share_i = raw_i.setScale(2, RoundingMode.DOWN)`; the leftover
  `amount - sum(share_i)` is allocated 0.01 at a time in listed order.
- Invariant: `sum(share.amount) == expense.amount` exactly, for every expense.

### Membership (FR-004, FR-008, FR-010, FR-011, FR-049)

One row per membership **period**. Join and leave history is the set of periods for a
`(groupId, userId)` pair; rejoining creates a new period and never changes historical source IDs.

| Field | Type | Null | Rules | Req. |
|-------|------|------|-------|------|
| id | UUID | no | primary key | FR-008 |
| groupId | UUID → Group | no | | FR-008 |
| userId | UUID → User | no | | FR-008 |
| joinedAt | Instant | no | start of this period; the "current join time" used for succession order | FR-008, FR-049 |
| addedById | UUID → User | no | the current Group Creator who added the user, or the creator themself for the founding membership | FR-007, FR-008 |
| leftAt | Instant [0..1] | yes | null while active; set at departure; `leftAt >= joinedAt` | FR-011, FR-049 |
| departureEventId | UUID → LifecycleEvent [0..1] | yes | the `MEMBER_REMOVED` or `MEMBER_LEFT` event; non-null exactly when `leftAt` is non-null | FR-049 |

Invariants:

- **Active membership** = a period with `leftAt` null. At most one active period exists per
  `(groupId, userId)`.
- Group access (FR-004, FR-010) requires an active membership at the time of each request.
  Ending the period revokes every access path: lists, details, receipts, reports, notifications,
  and operation replay.
- **Settled for departure** (FR-011): every `PairBalance` between the member and any other user
  in the group is 0.00. A scalar overall position of 0.00 is insufficient.
- Every pair balance between a departed member and any other user in that group is 0.00,
  because departure requires it and no new source record can involve a non-member.

## Derived read types (not stored)

All are computed by services and rules from source records; none is persisted. Field-level
service contracts are in [service-api.md](contracts/service-api.md).

### Balance derivation (BalanceCalculator; FR-031, FR-034)

For a group `g` and users `x ≠ y`, the signed amount from `x`'s view is

```text
pair(g, x, y) =   sum(shares of x in APPROVED expenses of g paid by y)
                - sum(shares of y in APPROVED expenses of g paid by x)
                - sum(CONFIRMED payments in g from x to y)
                + sum(CONFIRMED payments in g from y to x)
```

`pair(g, x, y) == -pair(g, y, x)`. For each group, the sum over all members of their signed
group positions is exactly 0.00 (FR-034). Pending, Rejected, and Cancelled expenses, and
Awaiting Confirmation, Declined, and Cancelled payments, are excluded (FR-031). Debts are never
simplified across a group or across different counterparties.

| Type | Fields | Rules | Req. |
|------|--------|-------|------|
| `PairBalance` | groupId, memberId, counterpartyId, counterpartyDisplayName, amount (signed Money), direction (`BalanceDirection`) | `amount = pair(groupId, memberId, counterpartyId)`; positive means `memberId` owes. `memberId` is the viewer in `myBalances`, or the departing member in a departure refusal or preview | FR-011, FR-031, FR-033 |
| `GroupContribution` | groupId, groupName, amount (signed Money) | one non-zero group term of a `CounterpartyBalance` | FR-032, FR-033 |
| `CounterpartyBalance` | counterpartyId, counterpartyDisplayName, byGroup (`List<GroupContribution>`, ordered by groupId), total (signed Money), direction | `total = sum(byGroup.amount)`; grouped by user ID, never display name; only the viewer's current groups; included when at least one contribution is non-zero | FR-032, FR-033 |
| `NetPosition` | amount (signed Money), direction | overall position = sum of all `CounterpartyBalance.total`; 0.00 and `SETTLED` when there are none | FR-032 |
| `PaymentAllowance` | groupId, payerId, receiverId, debt, reserved, available (all Money, never negative) | `debt = max(0.00, pair(g, payer, receiver))`; `reserved = sum(AWAITING_CONFIRMATION amounts in g from payer to receiver)`; `available = max(0.00, debt - reserved)`. Opposite-direction and other-group reservations never increase `available` | FR-037 |

Worked example (spec US5-AS4): B owes A 30.00 in G1, A owes B 10.00 in G2, B owes C 5.00 in G1.
For viewer B: A row `total = +20.00` with G1 `+30.00` and G2 `-10.00`; C row `total = +5.00`;
`NetPosition = +25.00` (B owes). Payment validation still uses only the per-group amounts.

## State transitions

Every transition below runs inside one top-level unit of work that holds the group's lock
(see [service-api.md](contracts/service-api.md)). A refused transition writes nothing.

### Expense

```text
[new] --record--> PENDING --final approval--> APPROVED   (terminal; immutable, FR-047)
                     |----any rejection-----> REJECTED   (terminal)
                     |----FR-049 cancel-----> CANCELLED  (terminal)
                     |----partial approval--> PENDING    (decision recorded; no status change)
```

| Arrow | Actor | Guard | Effect | Req. |
|-------|-------|-------|--------|------|
| [new] → PENDING | creator (session member) | group `ACTIVE`; creator, payer, and every participant are active members; at least one unique participant; amount, date, description valid; percentages valid for `PERCENTAGE`; approver set non-empty; receipt, if any, validated and finalized | insert Expense, ordered Shares, optional ReceiptRef, `EXPENSE_RECORDED` notifications, operation record; balances unchanged | FR-012 – FR-022, FR-025, FR-026 |
| PENDING → PENDING (partial approval) | required approver | expense `PENDING`; actor active member, in approver set, undecided; other approvers still undecided | insert `APPROVED` decision; no status change; no notification | FR-026, FR-027, FR-029 |
| PENDING → APPROVED | required approver | as above, and this decision completes approval by every approver | insert decision; status `APPROVED`; `EXPENSE_APPROVED` to creator; shares now participate in derivation (no balance row written) | FR-027, FR-029, FR-031 |
| PENDING → REJECTED | required approver | expense `PENDING`; actor active member, in approver set, undecided; reason nonblank | insert `REJECTED` decision with reason; status `REJECTED`; `EXPENSE_REJECTED` to creator; balances unchanged | FR-028, FR-029 |
| PENDING → CANCELLED | departure initiator (current Group Creator removing, or the member leaving) | expense `PENDING`; the departing member is its creator, payer, or participant (the approver set is a subset of payer and participants); departure is permitted under FR-011 | status `CANCELLED`; append `EXPENSE_CANCELLED` event; set `cancellationEventId`; `EXPENSE_CANCELLED` notification per recipient rules; decisions, shares, and receipt retained; balances unchanged | FR-049, FR-021, FR-025 |
| PENDING → [deleted] | creator | expense `PENDING`; actor is its creator and an active member | delete notifications, decisions, shares, ReceiptRef, and the expense in one unit of work; after commit remove the receipt file when no reference remains | FR-047 |

No transition exists from APPROVED, REJECTED, or CANCELLED. A decision, cancellation, edit, or
delete attempted on a terminal expense, or a second decision by the same approver, is refused
with no transition, no new decision, and no notification (US4-AS5, US4-AS9, US4-AS10).

### Payment

```text
[new] --record--> AWAITING_CONFIRMATION --receiver confirms--> CONFIRMED  (terminal)
                           |------------receiver declines----> DECLINED   (terminal)
                           |------------FR-049 cancel--------> CANCELLED  (terminal)
                           |------------stale confirm--------> AWAITING_CONFIRMATION (refused; no change)
```

| Arrow | Actor | Guard | Effect | Req. |
|-------|-------|-------|--------|------|
| [new] → AWAITING_CONFIRMATION | payer (session member) | group `ACTIVE`; payer and receiver are distinct active members; amount in FR-016 range; date present; note at most 200; `amount <= PaymentAllowance.available` | insert Payment (`recordedById = fromUserId`); `PAYMENT_RECORDED` to receiver; operation record; reservation now counted; balances unchanged | FR-035 – FR-037, FR-021 |
| AWAITING → CONFIRMED | receiver | payment `AWAITING_CONFIRMATION`; actor is `toUserId` and an active member; `amount <= max(0.00, pair(g, from, to))` recomputed live, without subtracting this payment's own reservation | status `CONFIRMED`; `decidedById`, `decidedAt`; reservation released; the payment now reduces the pair balance | FR-036, FR-037 |

| AWAITING → DECLINED | receiver | payment `AWAITING_CONFIRMATION`; actor is `toUserId` and an active member | status `DECLINED`; `decidedById`, `decidedAt`, optional `decisionReason`; reservation released; balances unchanged | FR-036 |

No transition exists from CONFIRMED, DECLINED, or CANCELLED; a repeated or wrong-actor decision
is refused with no change (US6-AS9).

## Departure transaction (FR-008, FR-011, FR-049)

`GroupService.removeMember` and `GroupService.leaveGroup` run this as **one** unit of work
holding the group lock. A member removing themself follows the leave path.

1. Acquire the group lock, open the unit of work, and resolve the operation ID (replay a
   committed result or refuse a reused ID; see the service contract).
2. **Authorize**: group `ACTIVE`; actor has an active membership; for removal of another member
   the actor is the current Group Creator; the subject has an active membership.
3. **Settled check**: compute `PairBalance` for the subject against every other user who has
   ever held a membership in the group. If any amount is not 0.00, refuse with the outstanding
   counterparty amounts and write nothing. Pending work alone never causes refusal.
4. Append the departure event (`MEMBER_REMOVED` or `MEMBER_LEFT`) with actor, subject, reason,
   and `Clock` time.
5. **Resolve pending work**: for each `PENDING` expense where the subject is creator, payer, or
   participant, set `CANCELLED` and append `EXPENSE_CANCELLED`; for each
   `AWAITING_CONFIRMATION` payment the subject sends or receives, set `CANCELLED` and append
   `PAYMENT_CANCELLED`, which releases its reservation. Genuine decisions, shares, and receipts
   are retained. No approval decision or receiver decision is written.
6. End the subject's membership period (`leftAt`, `departureEventId`).
7. **Creator role**: if the subject was the current creator, either transfer the role to the
   earliest-joined remaining active member (ties by ascending user UUID) and append
   `CREATOR_SUCCEEDED`, or, if none remains, archive the group and append `GROUP_ARCHIVED`.
8. Write cancellation notifications per the recipient rules (only remaining active members,
   never the initiating actor, never the departed member).
9. Write the operation record and commit.

On any failure before commit, roll back the entire unit of work: membership, events, statuses,
reservations, creator role, and notifications all remain as before (US2-AS12). After commit,
every access path of the departed member is refused on its next request because the membership
period has ended. Confirmed balances are unchanged by construction: only `PENDING` and
`AWAITING_CONFIRMATION` rows change status. No user, expense, share, genuine decision, payment,
or referenced receipt is deleted.

## Operational metadata (NFR-010, D-5)

These are implementation metadata, not customer financial entities.

### OperationRecord (NFR-010)

An actor-scoped record of a committed persistent command, written in the same unit of work as
the command's result. Its absence after the store is available proves the command did not
commit.

| Field | Type | Null | Rules |
|-------|------|------|-------|
| actorId | UUID → User | no | composite key with operationId; lookups are scoped to the session member |
| operationId | UUID | no | allocated by the controller per submission and reused for its retries |
| operationType | String | no | for example `RECORD_EXPENSE`, `APPROVE`, `CONFIRM_PAYMENT`, `LEAVE_GROUP` |
| fingerprint | String | no | SHA-256 hex of the canonical non-secret command fields (receipt content contributes its digest); never includes a password or credential buffer |

### schema_version (D-5)

Created by the startup migration runner before the first numbered script. Scripts live in
`src/main/resources/db/migration/` as `V001__initial.sql`, `V002__…`.

| Column | Type | Null | Rules |
|--------|------|------|-------|
| version | INT | no | primary key; script number |
| script_name | VARCHAR(200) | no | |
| checksum | CHAR(64) | no | SHA-256 of the script text; a mismatch with the bundled script refuses startup |
| state | VARCHAR(12) | no | `IN_PROGRESS` or `APPLIED`; the durable in-progress marker |
| started_at | TIMESTAMP WITH TIME ZONE | no | |
| applied_at | TIMESTAMP WITH TIME ZONE | yes | non-null exactly when `APPLIED` |

An `IN_PROGRESS` row is committed before its script runs and changed to `APPLIED` only after the
script succeeds. Because H2 DDL can commit independently, a remaining `IN_PROGRESS` row blocks
normal startup and requires recovery from the pre-upgrade backup. An unknown future version
also refuses startup without changing data.

### Service-enforced invariants (not row checks)

These span rows or tables and are enforced by services and rules under the group lock, with
JUnit coverage; they are not expressible as ordinary row `CHECK` constraints:

- shares sum exactly to the expense amount; percentages total 100.00; `percentage` present
  exactly for `PERCENTAGE` expenses (FR-014, FR-015, NFR-001);
- creator, payer, participants, and payment parties are active members when the row is written
  (FR-012, FR-013, FR-035);
- approver set non-empty, decisions only by undecided required approvers, and only on
  `PENDING` expenses (FR-026 – FR-028);
- payment amount within `PaymentAllowance.available` at recording and within live debt at
  confirmation (FR-037);
- an `ACTIVE` group's current creator holds an active membership; an `ARCHIVED` group has none
  (FR-049);
- departure only when settled, with pending work cancelled and the creator role resolved in the
  same unit of work (FR-011, FR-049);
- each group's signed positions sum to 0.00 (FR-034);
- lifecycle events are append-only and refer to the correct expense, payment, or successor for
  their type (FR-049).

No optimistic `version` column is modelled: the group lock serializes all writers of a group,
and a row version cannot protect derived debt.
